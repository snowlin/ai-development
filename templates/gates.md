# Gates

本文件保存 AI 开发协议的详细 Gate 清单。

读取规则：

- Simple 任务不读取本文件。
- Standard 任务只读取被激活的 Gate 章节。
- High-risk 任务读取对应 Gate 和 `Release / Rollback Gate`。
- Full audit 或上线前检查可以读取全部章节。

使用格式：

```text
Gate:
触发原因:
必须回答:
通过标准:
验证方式:
```

---

## 1. Idea Gate

触发条件：

- 用户只有灵感、想法、方向或一句话需求。
- 产品价值、目标用户或使用场景没有被定义。

必须回答：

- 为什么要做？
- 这个问题真实存在吗？
- 现在是在解决问题，还是被灵感牵着走？
- 一句话价值是什么？

通过标准：

- 能用一句话说明这个想法对谁有价值。

输出模板：

```text
Idea:
目标用户:
一句话价值:
不确定点:
是否进入 Product Gate:
```

## 2. Product Gate

触发条件：

- 新功能、新产品、新页面、新用户动作。
- 用户说“帮我做一个...”但没有明确边界。

必须回答：

- 谁用？
- 用来完成什么动作？
- 第一阶段只做什么？
- 不做什么？
- 什么不能伪装？
- 成功标准是什么？

通过标准：

- 能写出 MVP 边界和 Never Fake 清单。

输出模板：

```text
目标用户:
核心动作:
MVP 边界:
不做什么:
Never Fake:
验收标准:
是否进入 System Gate:
```

## 2.1 Product Selection Gate（可选）

触发条件：

- 新产品、新 SaaS、新 AI 功能或重大产品方向选择。
- 需要判断一个想法是否值得投入，而不是单纯执行已确认的需求。
- PRD 的关键要求主要来自未经验证的假设。

执行方式：

- 初始化项目只保留本触发规则，不复制完整方法论。
- 需要完整执行时，读取 `ai-development` 仓库模板 `templates/product-selection.md`。

必须回答：

- 谁是买方，触发时机和期望结果是什么？
- 当前内容哪些是事实、假设或未知？
- 最大未知是什么，最便宜的决定性测试是什么？
- 应该继续、定义后再做、放入停车场，还是拒绝？

通过标准：

- 交易、证据和下一步测试清楚；未经验证的假设不会直接变成开发需求。
- 人保留最终产品判断，AI 只负责生成选项、整理证据和设计测试。

## 3. System Gate

触发条件：

- 涉及核心对象、状态流转、数据流、AI/规则/人工边界。
- 用户需求会影响架构、模块职责或长期文档。
- 新产品、新功能或新页面需要进入实现前，先判断是否需要继续执行 System Skeleton Gate。

必须回答：

- 核心对象是什么？
- 数据从哪里来？
- AI 负责什么？
- 规则负责什么？
- 人工负责什么？
- 状态如何变化？
- 失败时怎么办？

通过标准：

- 能用 `输入 -> 处理 -> 输出` 写出数据流。
- 能说明对象、状态和失败处理。

输出模板：

```text
核心对象:
数据流:
AI / 规则 / 人工边界:
状态流转:
失败处理:
是否进入 Implementation Gate:
```

## 3A. System Skeleton Gate

触发条件：

- 新产品、新功能、新页面或新用户动作准备进入实现。
- 用户只描述了前台页面、按钮、表单、列表或局部功能，但没有描述用户体系、后台管理、权限和数据归属。
- 需求涉及登录、保存、历史、内容、订单、知识库、报告、导出、AI/API 调用、审核、发布、收费或运营处理。
- 开发中发现“还缺用户体系、后台、权限、管理入口、状态处理或异常流程”。

必须回答：

- 用户角色有哪些：游客、注册用户、付费用户、管理员、运营、审核员、团队成员？
- 后台角色是谁：谁管理用户、内容、订单、配置、日志、审核、封禁、退款或额度？
- 核心数据对象是什么：每个对象属于谁，是否需要 `owner_id`、`user_id`、`team_id` 或默认 owner？
- 权限边界是什么：谁能看、创建、修改、删除、审核、导出、发布？
- 状态如何流转：草稿、已提交、处理中、成功、失败、已发布、已归档、已封禁、已退款等是否存在？
- 后台管理最小能力是什么：列表、详情、编辑、禁用、审核、配置、日志、统计或人工处理？
- 异常场景是什么：失败、违规、重复、超额、误删、投诉、退款、模型失败、外部 API 失败怎么办？
- MVP 第一版做什么，不做什么，只预留什么？

通过标准：

- 能说明“谁使用、谁管理、数据属于谁、谁能改什么、出了问题谁处理”。
- 能区分本轮必须实现、只做最小预留、进入 Parking Lot 的系统骨架项。
- 如果暂不做用户体系或后台管理，必须写出延后依据、未来触发条件和最小预留策略。
- 前台功能不孤立开发，至少有对应的数据归属、权限、状态和管理处理说明。

输出模板：

```text
用户角色:
后台角色:
核心数据对象:
数据归属:
权限边界:
状态流转:
后台管理能力:
异常处理:
MVP 本轮实现:
最小预留:
暂不实现:
Parking Lot:
是否进入 Implementation Gate:
```

## 4. Implementation Gate

触发条件：

- 准备修改代码、脚本、配置、模板或文档。

必须回答：

- 这次只做哪个闭环？
- 修改哪些文件？
- 怎么验证？
- 失败如何回滚？
- 完成标准是什么？

通过标准：

- 本次任务能独立运行、独立验证、独立回退。

输出模板：

```text
本次闭环:
修改文件:
验证方式:
回退方式:
完成标准:
```

## 5. UI/UX Gate

触发条件：

- 新开发页面。
- 新增或修改页面、组件、交互、颜色、排版、信息层级。
- 用户说“不确定 UI 怎么做”“AI 生成 UI 后期要反复调”。

必须回答：

- Idea / Product / System Gate 是否已经通过？
- 本次 MVP 闭环和核心用户动作是否已经确认？
- 系统数据流是否已经能支撑该 UI？
- 本次是否需要 UI Draft First？
- UI 草图形式是什么：线框图、低保真 UI 图、ASCII 布局、Mermaid 流程、截图标注或可预览原型？
- 目标用户是谁？
- 用户进入页面后第一动作是什么？
- 页面核心信息是什么？
- 页面区域如何划分？
- 主要组件有哪些？
- 需要哪些状态：加载、空状态、错误、成功、禁用、编辑、确认、撤销？
- 是否有参考产品、设计系统、行业规范或 GitHub 示例？
- 中国用户是否更熟悉表格、筛选、明确按钮、强反馈、移动端优先或微信生态路径？
- 颜色是否服务于信息层级，而不是装饰？

通过标准：

- UI Draft First 位于 Product / System 之后、Implementation 之前。
- UI 草图没有替代产品定义、MVP 边界或系统数据流。
- 新开发页面已经先给出 UI 草图并得到方向确认。
- 主路径可完成。
- 页面状态完整。
- 颜色、布局、交互能说明原因。
- 不用后期靠大量 token 反复猜 UI。

可跳过 UI Draft First 的情况：

- 只改文案、图标、间距、颜色 token 或单个已有组件内的小样式。
- 已有确认过的设计稿、截图、Figma、参考页面或组件规范。
- 用户明确要求直接实现，并接受后续按实现结果微调。

参考标准：

- WCAG Accessibility。
- Apple Human Interface Guidelines。
- Material Design。
- Ant Design / Arco Design / TDesign。
- Nielsen Norman Group usability heuristics。

输出模板：

```text
前置 Gate:
MVP 闭环:
系统数据流:
UI Draft First:
草图形式:
目标用户:
主路径:
页面区域:
主要组件:
信息层级:
页面状态:
参考规范或产品:
中国用户适配:
颜色策略:
确认状态:
验证方式:
```

## 6. Data Gate

触发条件：

- 新增字段、表、集合、索引、缓存、导入导出、同步、迁移。
- 修改数据语义、状态、生命周期或数据质量规则。

项目阶段分流：

- **新项目 / 原型冷启动**：允许直接跑初始化建表/Migration 脚本，关注字段语义、索引合理性与基础 Migration 版本化。
- **已上线存量项目迭代**：必须硬性遵守“数据库变更优先于代码部署”及“向前兼容”约束。

必须回答：

- 数据来源是什么？
- 数据所有权属于谁？
- 字段含义、类型、必填、约束是什么？
- 【存量迭代】数据库 Migration 脚本是否优先于代码部署？代码是否能优雅处理新/旧字段缺失（向前兼容与 Fallback），避免直接抛出 500？
- 【存量迭代】是否涉及删除或重命名字段？若是，是否按 `Expand & Contract`（扩展与收缩/两阶段双写）拆分部署？
- 状态如何流转？
- 数据质量如何判断：准确性、完整性、一致性、及时性、唯一性、有效性？
- 数据如何迁移和回滚？
- 异常数据如何处理？

通过标准：

- 每个核心字段有语义。
- 存量项目变更不破坏当前在线代码的读写。
- 状态流转可解释。
- 异常和迁移有处理方式。

参考标准：

- W3C Data on the Web Best Practices。
- ISO/IEC 25012 data quality model。

输出模板：

```text
数据来源:
数据所有权:
核心字段:
项目阶段 (新项目/存量迭代):
Migration 部署顺序:
向前兼容/Fallback 策略:
Expand & Contract 计划 (如涉及删/改字段):
状态流转:
质量规则:
迁移和回滚:
异常处理:
```

## 7. Security Gate

触发条件：

- 认证、授权、角色、权限、支付、敏感数据、用户输入、Webhook、外部 API。
- Agent 权限、RAG、Prompt 注入、文件系统、命令执行、插件配置、hooks、scripts。

必须回答：

- 信任边界在哪里？
- 谁可以访问什么？
- 哪些数据敏感？
- 生产环境与开发/测试环境的 API Key 是否彻底隔离？
- 是否在提供商后台设置了 Hard Limit（硬上限强熔断，防止死循环刷爆额度）与 Soft Limit（软上限预警通知）？
- 输入如何校验，输出如何编码或脱敏？
- 外部 API、Webhook、依赖是否可信？
- Agent 是否可能执行越权操作？
- 审计日志和告警在哪里？

通过标准：

- 没有伪造认证、授权、支付、风控、审计或安全扫描结果。
- 生产 Key 与测试 Key 完全隔离，云服务/模型 API 配置了 Hard Limit 熔断。
- 高风险操作有验证和回退。
- 密钥、Token、个人信息不会进入代码、日志、测试快照或文档。

参考标准：

- OWASP Top 10:2025。
- OWASP ASVS 5.0.0。
- OWASP API Security Top 10 2023。
- OWASP Top 10 for LLM Applications 2025。
- NIST SSDF SP 800-218。

输出模板：

```text
信任边界:
权限模型:
敏感数据:
Key 环境隔离 (Dev/Prod 独立):
预算硬上限熔断 (Hard Limit / Soft Limit):
输入输出处理:
Agent / AI 风险:
审计方式:
验证方式:
```

## 8. Performance Gate

触发条件：

- 首屏、列表、搜索、批处理、接口、数据库查询、缓存、队列、模型调用、文件处理。
- 用户担心 AI 生成代码性能不可控。

必须回答：

- 受影响用户路径是什么？
- 核心指标是什么？
- 性能预算是什么？
- 前端风险在哪里？
- 后端风险在哪里？
- AI / 模型调用的延迟、并发、重试、缓存如何处理？
- 重试机制是否配置了“错误鉴别器”（区分网络超时/偶发 5xx 等可重试错误 + 指数退避，以及 4xx 客户端错误/SQL Schema 错误如 `column does not exist` 等确定性失败立刻终止并告警）？
- 如何观测和验证？

通过标准：

- 指标可测量。
- 严禁无差别自动重试，确定性失败有立刻终止与告警机制。
- 验证命令或手动步骤可复现。
- 性能风险有降级或回退方式。

参考标准：

- Core Web Vitals：LCP <= 2.5s、INP <= 200ms、CLS <= 0.1。
- Lighthouse。
- OpenTelemetry：Traces、Metrics、Logs。
- 后端指标：P50/P95/P99、QPS、错误率、CPU、内存、数据库耗时、缓存命中率。

输出模板：

```text
受影响路径:
核心指标:
性能预算:
重试错误鉴别策略 (指数退避 / 确定性失败终止告警):
风险点:
观测方式:
验证方式:
降级或回退:
```

## 9. AI Evaluation Gate

触发条件：

- Prompt、模型、Agent、RAG、自动分类、自动总结、自动决策、推荐排序。

必须回答：

- AI 的任务边界是什么？
- 输入样例有哪些？
- 期望输出是什么？
- 如何评价正确性？
- 失败、幻觉、越权、拒答如何处理？
- 哪些结果必须人工审核？
- Prompt、模型、参数、数据集版本如何记录？

通过标准：

- AI 行为可评估。
- 失败样例被覆盖。
- 人工审核边界明确。

参考标准：

- NIST AI RMF。
- OpenAI Evals。
- OWASP LLM / GenAI guidance。

输出模板：

```text
AI 任务:
输入样例:
期望输出:
评价方式:
失败处理:
人工审核:
版本记录:
```

## 10. Human Judgment Gate

触发条件：

- AI 输出会影响产品方向、架构、安全、性能、成本、商业判断、UI 审美、学习路线或高风险决策。
- AI 给出结论但没有明确证据。
- AI 的表达很流畅，但用户无法判断其真实性、重要性或代价。
- 用户说“我没把握”“听起来对但不确定”“这个是不是 AI 在猜”。

必须回答：

- 哪些是 Checkable Evidence：可验证事实？
- 哪些是 AI Assumption：AI 推测？
- 哪些是 Human Judgment：需要用户亲自判断的价值取舍？
- 是否存在 Counterexample：相反观点、失败案例或边界条件？
- 如果判断错误，代价是什么？
- 下一步如何验证？

通过标准：

- 没有证据的内容被标记为推测。
- 用户能看出哪些部分必须自己判断。
- 至少列出一个反例、失败场景或边界条件。
- 给出可执行的下一步验证方式。

输出模板：

```text
Checkable Evidence:
AI Assumption:
Human Judgment:
Counterexample:
Wrong-if Cost:
Verification:
```

## 11. Context Management Gate

触发条件：

- 对话超过一个闭环。
- AI 连续给出不一致方案、重复错误、引用过期事实或忘记前置约束。
- 任务从探索切换到实现、从实现切换到调试、从调试切换到发布。
- 用户说“上下文乱了”“前面不是这样说的”“重新梳理一下”。

必须回答：

- 当前目标是什么？
- 已确认的产品、系统、UI、数据、安全或实现决策有哪些？
- 当前活跃 Gate 是哪些？
- 哪些上下文可能过期、冲突或未验证？
- 是否需要压缩上下文、重开任务或重新读取文件？
- 下一步只继续哪个闭环？

通过标准：

- 当前可信上下文被列出。
- 过期、冲突、未验证上下文被标记。
- AI 不继续基于旧对话残留执行。

输出模板：

```text
当前目标:
已确认决策:
活跃 Gate:
可信上下文:
过期或冲突上下文:
建议动作:
下一闭环:
```

## 12. Trust Calibration Gate

触发条件：

- 准备把决策、实现、验证、重构、依赖选择或发布操作交给 AI。
- 任务涉及生产、数据、安全、权限、成本、模型行为或团队协作。
- 用户担心“是不是太相信 AI 了”。

必须回答：

- 当前任务风险等级是什么？
- AI 权限级别是 Suggest、Draft、Modify 还是 Execute？
- 哪些步骤 AI 可以直接做？
- 哪些步骤必须用户确认？
- 哪些操作禁止 AI 自动执行？
- 信任依据是什么：测试、类型检查、文档、人工 review、外部证据？

权限级别：

| 级别 | 含义 | 适用 |
| --- | --- | --- |
| Suggest | 只给建议，不改文件 | 产品方向、架构取舍、高风险判断 |
| Draft | 生成草案，等待确认 | 文档、UI 草图、实现方案、测试计划 |
| Modify | 可改文件，但必须验证 | 标准闭环、低风险代码和文档 |
| Execute | 可执行命令或发布步骤 | 已确认且可回滚的低风险自动化 |

通过标准：

- AI 授权边界明确。
- 高风险操作有人工确认点。
- 不把 AI 的自信语气当成信任依据。

输出模板：

```text
风险等级:
AI 权限级别:
AI 可直接做:
必须用户确认:
禁止自动执行:
信任依据:
```

## 13. Dependency Gate

触发条件：

- 新增、升级、移除依赖。
- 修改运行时、构建工具、包管理器、插件、MCP、hooks 或脚本。

必须回答：

- 依赖用途是什么？
- 为什么现有能力不够？
- 版本如何锁定？
- 维护状态、许可证、安全风险是什么？
- 体积、安装时间、冷启动是否受影响？
- 移除成本是什么？

通过标准：

- 依赖的价值大于维护成本。
- 有替代方案或移除路径。

## 27. AI 产品上线前必过 5 道关卡 Check List

用于产品从开发转入生产发布前的快速核对清单。

### 阶段适用指引
- **0 到 1 新项目（原型期/冷启动）**：数据库可直接跑全量 Migration 脚本；重点防范 API Key 泄露、预算硬上限与基础坏路径。
- **1 到 N 存量项目（已上线/有用户/滚动发布）**：必须严格执行全部 5 道关卡，尤其是数据库变更先行与错误鉴别/幂等控制。

---

### 1. 数据库变更优先于代码部署 (Data Gate & Release Gate)
- **核心原则**：数据库 Migrations 必须在先，代码上线在后。
- **执行细节**：
  - 【新项目冷启动】：直接跑全量版本化 Migration 脚本。
  - 【存量在线迭代】：新代码必须实现向前兼容（`NULLABLE` / `DEFAULT` 与优雅 Fallback），避免旧 Schema 字段缺失抛出 500；涉及到删列或改列，必须采用 `Expand & Contract`（两阶段扩展与收缩双写）策略拆分发布。

### 2. 为任务重试机制配备“错误鉴别器” (Performance Gate & System Gate)
- **核心原则**：严禁无差别自动重试，区分可恢复错误与确定性失败。
- **执行细节**：
  - **可重试**：网络超时、偶发 5xx 等，需配置指数退避（Exponential Backoff）策略。
  - **不可重试**：4xx 客户端错误、数据库 Schema 错误（如 `column does not exist`）等确定性失败，必须**立即终止任务并触发告警**，禁止进入重试队列。

### 3. 涉及计费 API 的任务必须实现幂等性 (Cost Gate & Productization Gate)
- **核心原则**：假设任何调用外部付费 API 的任务都会被重复执行，设计为支持“从断点继续”。
- **执行细节**：
  - **记录状态**：任务启动与各个子步骤完成后，在数据库中更新任务状态（如 `task_id` + `status`）。
  - **断点重试**：任务重试时优先查询历史记录，跳过已完成的高成本 API 调用（如 LLM 推理），仅执行未完成的步骤。

### 4. 彻底隔离环境 API Key 并设置预算硬上限 (Security Gate & Cost Gate)
- **核心原则**：生产与测试环境完全隔离，建立成本熔断机制。
- **执行细节**：
  - 生产环境与开发/测试环境必须使用独立的 API Key。
  - 在服务商后台配置 **Hard Limit（硬上限）** 防止死循环消耗额度，同时配置 **Soft Limit（软上限）** 触发 Slack 或邮件警报。

### 5. 上线前进行“坏路径”（Bad Path）场景测试 (Verification Gate & Production Gate)
- **核心原则**：不能仅验证 Happy Path，必须显式测试系统在边缘异常情况下的表现。
- **执行细节**：
  - **测试场景**：断网/数据库断开、第三方 API 持续 500、并发重复触发同一任务、API 额度耗尽等。
  - 验证系统在出现上述异常时是否能够优雅降级或安全终止，防止费用无限放大。
